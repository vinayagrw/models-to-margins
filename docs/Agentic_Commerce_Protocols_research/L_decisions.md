Inputs: W3_redteam.md (C1 to C20), W3_K1 to K6, G1_gapclose.md (G-01 to G-57), G2_gapclose.md (G-101 to G-136). Each decision says what changes and where. "Doc" is `docs/Agentic_Commerce_Protocols_Technical_Design.md`. "Data" is the fragments in `drafts/acx/frag/`. Section 13 of the doc cites these ids.

## Recommendation and architecture

- **D1. Thesis restated (C1, C2, C9, C3).** Old: build to the token and the mandate, not the protocol. New: spend first on what pays in every world (product data, agent order tagging, the evidence record). Build to the token and a thin authority record, not to any one checkout protocol, only once your own agent order share passes a dated trigger. The thesis now has a losing world: if platform wallets own both token and checkout (scenario "walled"), integrate those platforms directly (ADR-1 option A). Doc: section 3, ADR-1 title and text, section 15. Data: none.
- **D2. ADR-1 gets option D, wait with readiness (C3, G-01 to G-06, G-42, G-44).** Keep the PSP, fix product feeds and agent order tagging, keep the evidence record, and watch. It is the default below the trigger. Trigger: your own agent completed share (V17) passes 3% of orders for two months running, or a network or platform starts publishing agent orders by checkout surface. Above the trigger, option B (canonical model plus adapters) applies. The revisit rule changes from "one protocol passes a majority of agent orders" to that surface based trigger, because the only split anyone measures is by platform (G-03). Option B cost is stated per breaking release, with UCP's 23 breaking items in two 2026 releases as the example (G-37, G-38). The 5K to 500K USD per standard range is unverified and only quoted as such (G-41). Doc: 5.4 ADR-1, 8.2, 15.
- **D3. Authority record, not mandate core (C2, G-16, G-17).** The canonical Authority record holds five common fields (amount cap, currency, merchant constraint, expiry, recurrence) plus a binding level (cart, session, merchant, amount only) plus the original signed artifact stored unchanged. Adapters map into the common fields and never rewrite the artifact. A UCP adapter is a checkout session state machine, not a thin translator, and the doc says so. Doc: 5.3, 3.
- **D4. ADR-3 narrowed, spend caps move to the buyer side (C4, G-16, G-17).** The merchant gateway checks the cart against the authority record (AP2 closed mandate, ACP token scope) and writes evidence. It cannot stop manipulation that happens on the buyer side before signing. Per agent spend caps across merchants (V1) and budgets belong to the agent platform or the network. Visa already enforces the cap at credential retrieval. Remove the claim that a forged cart cannot also be approved. V1 "who decides" becomes agent platform or network. Doc: 5.4 ADR-3, 4.2 V1, 7.6, 5.2 (the "Enterprise buying agents" box is a buyer side product, say so). Data: d1a vars V1 who, d1b arch.components if a component claims cross merchant caps.
- **D5. ADR-5 drops seller held prepaid agent balances (C4).** Holding prepaid balances for agents may be stored value that needs a licence. Pay per call settles through a facilitator using x402 upto or batch settlement, both now merged in the spec, with Coinbase CDP support on five EVM mainnets (G-133 to G-135). Doc: 5.4 ADR-5, V15. Data: d1b arch.components if affected.
- **D6. ADR-2 tier 2 rule (C12, G-34, G-36).** Tier 2 accepts either a valid agent signature plus a valid mandate, or a network registered agent plus an agentic token plus a passkey at set up (the live Visa EU flow). Unsigned agentic browsers are not refused at payment. They go to normal card not present risk scoring. Add Cloudflare's Direct or Intermediary flag to P3 values. Doc: 7.6, 5.4 ADR-2, 8.1 verdict item 3, 4.1 P3.
- **D7. ADR-4 wording and a privacy owner (C18, G-18, G-33, G-55).** Writing evidence first improves the odds in a dispute. It does not guarantee a defence, because no network has said it accepts a mandate as compelling evidence (Visa Intelligent Commerce names the purchase instruction as dispute evidence, G-18). The store keeps evidence only for the longest dispute window of the rail used, then deletes (new V18). Add a seventh persona, Noor, privacy and data protection lead, who owns V18 and the store. Widen Ravi to fraud and issuer risk (C10). Doc: section 0 panel, 1.2 retention line, 5.4 ADR-4, 5.3 owner of the evidence store. Data: d1b arch.components evidence store persona Noor.
- **D8. ADR-6 filled in with what each route says (K3, G-116, G-124, G-125, G-127, G-35).** Visa rule 4.1.23.10: the cardholder is responsible for an enrolled agent. Mastercard: no rule text found, its developer guide says standard chargeback rights apply. Stripe Link: the user is responsible for every purchase the agent makes, including wrong items. UK PSRs 2017 reg 77(4)(c) and (d): the payer carries no loss for an unauthorised online payment or one where SCA was skipped, and whether an in mandate agent payment is authorised is unsettled (our reading, not a regulator view). Cloudflare's coalition post says the site pays when a user disputes an agent purchase. Amex Agent Purchase Protection is promised and not yet available (G-24). Doc: 5.4 ADR-6, 7.2, 7.3.
- **D9. Signed webhooks in the adapters (G-129, G-131).** ACP order webhooks must carry an HMAC-SHA256 Merchant-Signature. UCP webhooks must be signed with RFC 9421, ES256 baseline. Neither requires signed payment authorization responses. The adapters verify signatures and timestamps and keep one HMAC secret per platform. Doc: 5.3 adapters, 7.6 table.
- **D10. Latency target marked untested (C19).** The 300 ms p95 stays as a target and the doc says no production p95 for Web Bot Auth or TAP checks was found. Doc: 1.2, 5.5.

## Patterns, tree and criteria

- **D12. Two more patterns (C6, G-08, G-19).** Pattern 5, single use virtual card (interim, Mastercard calls it a bridge it will not support long term). Pattern 6, unrecognised agent with a stored card (an agentic browser on the normal checkout, scored by the issuer as an ordinary card not present sale). Doc: 8.1 with a short sequence or note for each and rows in the comparison. Data: d1b `patterns` add ids `vcard` and `browser` with the same fields as the others.
- **D13. Tree leaves anyone can build (C17, G-34, G-48, G-49).** Add a first question: does the agent present an agentic token or a mandate at all? No leads to `browser`. Doc: 8.3 and its Mermaid block. Data: d1b `tree`, every yes and no must resolve.
- **D14. Criteria and weights (C10, C11, G-42, G-43, G-44).** Liability clarity leaves the weights and becomes a gate: a route passes only if ADR-6 names who carries the loss. New weights: where your buyers' agents already are 20, rail fit 20, fraud and identity exposure 15, integration and PSP support 15, data and catalog readiness 10, maturity 10, openness of governance 10. Basis, stated plainly: a panel judgement anchored on survey barrier ranks (identity and fraud top barrier at 41 percent, data readiness 34 percent, G-43) and on 84 percent of merchants reporting no demand (G-42). Add a sensitivity line showing which results flip when 10 points move. Doc: 8.2. Data: d1b `criteria` with the new list, plus one item for the gate with `"weight": 0, "gate": true`.
- **D15. Worked example compares inside a layer (C11, C20).** Replace the cross layer ranking in 8.4 with two comparisons: checkout surface (UCP, ACP, Copilot Checkout, an agentic browser on the merchant site) and credential (network agentic token, Stripe SPT, single use virtual card), each scored with the D14 weights, every score with a claim id or marked illustrative, and the sensitivity line.
