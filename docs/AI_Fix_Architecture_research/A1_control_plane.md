## 1. Reference architecture in words

### 1.1 Two halves

- **Control plane.** The place where the organisation keeps its settings: which model version is allowed, which sources are allowed, the date rules, the claim-check thresholds, the budgets and the test set. Each setting is versioned, so any change is a release that can be tested and rolled back.
- **Data plane.** The path each live request takes. It reads the settings and enforces them, request by request.

This split is our design framing. Kong describes its product as a control plane for AI traffic (AR1-12), and the Azure Architecture Center describes one control plane with gateways copied into each region (AR1-15). No standards body page we opened defines the split for AI.

### 1.2 The order a request passes through

1. **Entry and identity.** The app calls one internal endpoint, not the model provider. The gateway checks who is calling (team key, app identity) and which policy set applies. (P6)
2. **Budget and quota check.** Before any model call, the gateway checks the caller's spend cap and token rate limit and refuses the call if it is over. Azure API Management can count prompt tokens before the call to save a wasted request (AR1-14). (P6)
3. **Input screening.** Personal data masking, prompt attack screening and topic rules run on the prompt. (Related block, not in scope here, but it sits at this step.)
4. **Source and date rules.** If the answer needs outside facts, the retrieval or web tool runs with an allow list or deny list of domains and a freshness rule. The model may only cite a page it has actually fetched and read in this session (read-before-cite). (P2)
5. **Route to a pinned model.** The router sends the call to an exact model version ID, never a floating alias. If that model fails, fallback goes only to a copy of the same model at the same version. The Azure Architecture Center says not to fail over from version X to X+1 (AR1-16). (P6)
6. **Model answers.** The answer comes back with citations that point at the exact source passages.
7. **Claim check.** A separate checker splits the answer into claims, ties each claim to a quoted sentence in the sources, scores it, and then blocks, flags or corrects the answer. This is a different model or classifier from the one that wrote the answer. (P1)
8. **Output screening.** Safety classifiers and a "does every claim have a citation" check run on the final text.
9. **Return to user** with citations and, where the check flagged something, a visible warning.
10. **Log and trace every step.** Each step writes a trace span: model ID asked for, model ID that answered, tokens, cost, sources fetched, claim-check score, policy decisions. OpenTelemetry GenAI conventions give common field names (AR1-38). Prompt and answer text capture is opt-in in that standard (AR1-39). (P6, P10)

### 1.3 The offline loop (P10)

11. **Test set gate.** Any change to the control plane (new model ID, new prompt, new threshold, new source list, new retrieval setting) runs the organisation's own test set first. The change ships only if the pass rate stays above the agreed bar. promptfoo documents failing a CI build below a pass rate (AR1-36).
12. **Canary set on a schedule.** A small fixed set runs daily against production, because providers change things on their side too. Example: in October 2026 Azure AI Content Safety began rolling a new classifier model, region by region, and said some text "might receive different classifications" (AR1-56).
13. **Feed back.** Failures found in production traces become new test cases.

## 5. Gaps

1. **No neutral AI gateway reference architecture.** We found no standards body (NIST, ISO, OWASP) or peer-reviewed reference architecture for an AI gateway or LLM control plane. The closest neutral source is the ICSA 2025 Swiss Cheese guardrail paper, which is agent focused. The cloud architecture centre pages are vendor authored.
2. **No independent measurement (rung 3) of any claim checker.** None of the pages opened gave false positive or false negative rates for Bedrock grounding, Vertex check grounding, Azure groundedness, NeMo fact rails, AlignScore, Lynx or HHEM. Thresholds on vendor pages (0.5, 0.6, 0.7) are defaults or advice, not tested error rates. This is the largest gap for P1.
3. **Missing prices.** Vertex check grounding price (pricing page truncated), Azure groundedness Standard price (shown as "$-"), Azure API Management tier prices (not opened), OpenAI web search and Perplexity prices (not read).
4. **Freshness rules are mostly do-it-yourself.** Only Perplexity offers a recency filter among the options checked. Anthropic exposes page_age and retrieved_at, but no tool enforced a "no source older than N days" rule natively.
5. **Read-before-cite is partly built in.** Anthropic web fetch only fetches URLs already seen in the conversation and can attach citations, but no vendor tool we opened blocks a citation to a page that was searched but not fetched. That check belongs in the claim-check step.
6. **Eval gating on model change is not a gateway feature.** None of the gateways opened (LiteLLM, Portkey, Kong, Cloudflare, Azure APIM, Unity Gateway) documented running a test set automatically before a model pin changes. The gate has to be built in CI with promptfoo, Inspect, Langfuse datasets or similar.
7. **Licence detail.** Kong AI plugin licence (OSS or enterprise) not confirmed. Llama Guard 4 licence not on the page opened. Ragas licence not on the page opened.
8. **OpenTelemetry GenAI status.** Still "Development". Date of the move to the separate repo not found.
9. **Pages we could not open.** Langfuse changelog (404), AWS What's New generative AI page (404), Kong 2.0 blog (404), C1.ai press release (403). Their content is not used except as rung 7 rows.
10. **Ownership churn.** promptfoo, Portkey, Guardrails AI and Langfuse all changed owner in 2026. We found no licence change, but roadmap and support terms may change. Worth re-checking before any design commits to one of them.
